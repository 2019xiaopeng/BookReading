## 一·四、阅读时长与状态修正 + 手动状态（2026-11-12 用户提出，已设计待实施）

**根因（代码实证）**：
- ①最小化仍计时：计时只查 `document.visibilityState==="visible"`（ReaderPage.tsx:772）——**Tauri 最小化不触发 WebView 的 visibilitychange**，窗口缩到任务栏后照计
- ②<1 分钟不显示"已读"：formatReadingTime 对 <60s 返回 null，chip 直接不渲染
- ③切"在读"过滤书不出现：readingStatus.ts:5 规定 percent≤0=未读——刚开的书进度还是 0，永远进不了"在读"
- ④用户要手动设状态：现在状态纯由 percent 推导，无覆盖入口

**设计**：

| # | 项 | 方案 |
|---|---|---|
| S-1 | 计时失焦即停 | 判据改为 `visibilityState==="visible" && document.hasFocus()`，另听 Tauri `getCurrentWindow().onFocusChanged`（blur 含最小化→暂停，focus→恢复）；与微信读书同语义：窗口不在前台就不算阅读。flush 时机不变（60s/隐藏/关书） |
| S-2 | <1 分钟也显示 | formatReadingTime：<60s 返回 `"<1 分钟"`（不再 null）；已有 0<n<60 秒书库数据即刻上 chip |
| S-3 | 在读语义修正 | 推导规则改为：**从未打开（last_opened_at==null）且 percent≤0 = 未读；打开过且 <95% = 在读**（"未读"=没碰过的书，"在读"=翻开过没读完的）；≥95% 仍=已读 |
| S-4 | 手动状态覆盖 | books 表加列 `manual_status`（NULL=自动｜unread/reading/finished）；书卡 ⋯ 菜单与详情弹窗加"状态"子菜单：未读/在读/已读/**恢复自动**；过滤与统计一律 `manual_status ?? 推导值`。已读判定不因手动"在读"被 percent 顶掉（手动优先） |
| S-5 | 联动 | 设置手动"已读"不强制改 percent（进度条照旧）；统计列"在读 N"用同一合并口径；迁移=ALTER TABLE ensure 模式（存量 NULL=自动，零变化） |

**验收**：最小化/切窗 10 秒不计时，回焦继续；读 20 秒关书回架 chip=已读 <1 分钟；刚开的书立即出现在"在读"；手动标"已读"的书过滤与统计一致，恢复自动后回到推导值。

## 一·六、阅读偏好默认值（2026-11-12 用户提出，已设计待实施）

**现状机制**（v2.5 E2/v2.6 epuset 已有）：书内改设置（漫画：方向/适配/单双页/条漫宽度/双页偏移；EPUB：字号/行距/排版细项）→ 只钉当前书（imgset/epuset 覆盖键）；全局键=新书的默认。**缺口**：漫画这些字段只能在书内改（改了就钉书），没有"把这配置变成我的默认"的入口——新书永远从出厂态开始，用户每个习惯（双页、RTL）都要新书重调。

**设计（不推翻覆盖机制，补反向入口）**：

| # | 项 | 方案 |
|---|---|---|
| G-1 | 「设为我的默认」 | 漫画/EPUB 设置面板底部一行：**将当前生效配置保存为默认**（写全局键；toast「新书将使用此配置」）。你的取舍担忧由此化解：默认=你的阅读习惯；个别不符合的书在书内改=自动钉书级，互不传染 |
| G-2 | 「本书恢复默认」 | 面板显示"本书已单独设置"小 chip（imgset/epuset 覆盖存在时）+ 一键清除本书覆盖回到默认 |
| G-3 | 两阅读器同款 | ImageSettingsPanel 与 EPUB SettingsPanel 同一对按钮同一套文案——一个心智模型管两处 |

**验收**：书内调 双页+RTL → 点"设为我的默认" → 开一本新漫画直接双页+RTL；原书配置不动；新书书内再改只钉新书；"本书恢复默认"后回默认态。

## 一·七、书架（文件夹）在混排视图中的排序与计数（2026-11-13 用户提出，已设计待实施）

**现状（代码实证）**：网格渲染顺序恒为 新建卡→书架卡→书卡（LibraryPage.tsx:1330-1401）；置顶只让书在**书区**内领先（:180），永远排在全部文件夹之后；书架计数只算直属书（shelves.ts:56 countByShelf）；书架排序只有 sort_order 兜底名序（shelves.ts:3），**没有任何排序入口**（拖拽手势已被"拖入嵌套"占用，不能复用做排序）。

**取舍**：混排单序列（文件夹和书互相穿插拖动）需要统一坐标 schema，改动大收益低——**采纳用户认可的分组模型**：文件夹组与书组各自排序，置顶语义修正为真·最顶。

| # | 项 | 方案 |
|---|---|---|
| K-1 | **置顶书浮到全网格最顶** | 渲染顺序改为：置顶书 → 新建卡 → 书架组 → 普通书组。"置顶"=无视分组的真最顶（微信读书同款直觉）；置顶多本之间仍按当前排序键 |
| K-2 | **文件夹组排序入口** | 排序菜单在**含子书架的视图**追加"文件夹排序"段：默认（创建序）/ 书名升降 / 书数降序；settings 键 `folder_sort` 持久化。不做拖拽排序（手势冲突：拖书架到书架=嵌套，加"拖到间隙=排序"学习成本高，≤10 个书架不值） |
| K-3 | **计数含子孙** | countByShelf 改递归版（直属+全部后代）；卡面"N 本"=总数，title 提示补"直属 n · 含子书架 m"；+N 徽章与四宫格仍用直属书（视觉口径不变） |
| K-4 | 侧栏树计数（可选顺手） | 侧栏书架名后小数字（同一递归计数，muted 色）；让"哪个架书多"不进视图也可见 |

**验收**：置顶书出现在新建卡之上；文件夹按所选键排；嵌套书架卡显示含后代总数；侧栏计数与卡面一致。

## 二、ponytail 代码审计发现（2026-11-12，v2.6.0 后全库）

**审计范围**：本仓库是一个 Windows 单用户桌面阅读器（Tauri+React+Rust+SQLite）；假设负载=单用户单进程，**外加一个真实两进程场景：正式版与 dev 版同时开（共享同一 SQLite，WAL 已护库）**。重点通读：epub_optimize.rs 全文、scan_health、tts.ts、HealthScanDialog 删除链、delete_books_from_disk；未逐行读：ReaderPage 全文、weread.css、存储迁移老代码。

### Must fix

1. **`.part` 临时文件并发碰撞**（`src-tauri/src/commands/epub_optimize.rs:179-183`）
   - **是什么**：优化副本写到固定名 `{opt}.part` 再改名上位。
   - **问题**：启动后台补生成线程与"强制重导入同书"的导入内联优化可能同时处理同一本——两个写者互踩同一个 .part，损坏的 zip 被 rename 成正式 .opt，阅读器打开即失败。
   - **修法**：临时名加唯一后缀（`{stem}.opt.{uuid}.part`），rename 前谁先写完谁上位。一行级。
   - **不修的后果**：低概率但属于数据完整性类；出错时用户需手删 .opt 才能恢复阅读。

### Should fix

2. **scan_health 的 basename 重复键是死逻辑**（`src-tauri/src/commands/library.rs:967-974`）
   - **是什么**：复制入库的文件名是 uuid，basename 键永不成组；注释声称"与前端同口径"但前端用的是导入时源文件名。
   - **问题**：不产生错误结果，但误导后来者以为它在工作。**修法：删掉该分支**（title+size 单键已覆盖真实重复），删优于改注释。
3. **大写扩展名口径不一致**（`epub_optimize.rs` 候选用 lowercase 判 `.epub`；`reader.ts` 探测只匹配小写 `/\.epub$/`）
   - **问题**：用户导入 `BOOK.EPUB` → 后台生成了 .opt 却永不被前端使用（白占磁盘）。**修法**：导入时扩展名统一转小写（源头归一）。

### Nice to have

4. **TTS 单段失败即停整队**（`src/reader/tts.ts:94-96`）：`onerror` 置 idle 不续播——一章中某段引擎报错就全停。可改为"错误也前进"并加连续失败熔断；一期可接受。
5. **301MB 级书导入内联优化耗时 200s+**（`import_book` 同步调用 optimize）：导入进度条全程"导入中"易被误认为卡死。可把内联改为"入库即返、首启 backfill 兜底"，或导入提示文案注明"正在优化插图"。

**Verdict:** 健康可发。#1 建议随 v2.7 首批修（一行级），#2/#3 顺手清。
**Lean:** scan_health 死分支 -8 行。
**Not checked:** ReaderPage 3 万行全文、CSS、存储迁移深路径；正式版+dev 双进程下 settings 写穿互相覆盖（用户级风险=设置抖动，非数据丢失，未深查）。
